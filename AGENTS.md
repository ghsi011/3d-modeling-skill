# AGENTS.md

* Treat every design request as an end-to-end commission: create, assess, package, retain, and document it without requiring the user to organize the workflow.
* Store every project under `C:\projects\3d\<project-slug>\`; keep all requests, photos, source CAD, editable models, exports, renders, settings, receipts, tests, and physical feedback there.
* Never place project-specific models, large binaries, private evidence, or licensed third-party artifacts in this skill repository.
* Preserve the original request and source files unchanged. Record hashes, units, transforms, assumptions, decisions, tolerance provenance, manufacturing context, and validation status.
* Never overwrite design history. Create a new revision for corrections and a separate alternative for competing concepts; retain ancestry, differences, artifacts, and outcomes.
* Ask the user only when missing information blocks a reliable design or requires a real preference. Otherwise derive what is safe, state assumptions, and continue.
* Produce the smallest complete deliverable set: editable source, manufacturing exports, relevant assembly or print instructions, assessments, and explicit unresolved physical tests.
* Keep software assessment, independent review, successful printing, physical fit, motion testing, and user confirmation as distinct evidence states.
* After every real job, write a compact learning record. Keep project-specific lessons with the project; promote only repeatable, evidence-supported lessons into skill code, fixtures, patterns, calibration data, or documentation.
* Never generalize fit allowances, tolerances, shrinkage, material behavior, or printer calibration beyond the conditions actually tested.
* When a real job exposes a skill defect, add a failing regression fixture, implement the smallest architecture-consistent fix, run the affected replay, and update the roadmap only when the missing capability is broader than the defect.
* If a defect can produce a false successful claim or violates an authority invariant, fail the affected claim path closed immediately and stop dependent work until a regression test proves the repair. Unaffected work may continue only with its limitations explicit.
* Follow `ARCHITECTURE.md` and `ROADMAP.md`; preserve proportional effort, candidate-independent acceptance, explicit uncertainty, branch isolation, and minimal context and AI dispatch.
* Treat authored or generated model code as untrusted implementation input. Never import it into the process that owns planning, acceptance, assessment, reviews, or final status; execute it only through the approved confined build boundary, which must reduce its authority by the operating system and bound its lifetime, not merely give it another interpreter.
* Inspect existing code and conventions before changing the skill. Avoid unrelated refactors, duplicate authorities, speculative abstractions, and unnecessary agents.
* One writer per worktree. Never run two agents that write to the same checkout, and never commit to a branch while an agent is working in it — a commit rewrites the working tree and silently discards uncommitted work, including work you asked for. `git checkout -- <path>`, `git restore`, `git reset --hard` and `git clean -f` are the same class and are more dangerous, because they are reached for *as* a way to undo something: a mutation sweep that reverted each patch with `git checkout --`, from a tree whose implementation was not yet committed, destroyed it on the first revert — and the twelve mutations after it reported a missing anchor against a file that no longer held the code, so the sweep also stopped measuring anything. Whatever restores state must restore it from bytes it read itself, not from `HEAD`, which is the intended baseline only when the tree is clean. Record `git rev-parse HEAD` and `git status --short` at the start and end of any run that depends on the tree, and stop rather than continue if either moved. Read-only work may run alongside a writer; a job that executes the tool under test is not read-only.
* Assume the checkout is ephemeral. Commit and push each coherent slice *before* dispatching its review, not after — a review cannot run on work a reclaimed container took, and the only slice ever lost that way was the one held back to be reviewed first. After a reclaim the tree returns at the last pushed commit with **stale `origin/*` refs**: `git fetch` before reading them, or a cached pointer will have you reporting safe work as destroyed. Give reviewers a copy of the tree, so the writer keeps working.
* A hosted check that did not pass has not necessarily failed, and the difference decides what to do next. Read the data, not the rendering: `gh run view <id> --json status,conclusion,jobs` gives each job's and step's own `conclusion`, and `gh run watch <id> --exit-status` holds one connection instead of polling. `gh run watch` prints the same mark for `cancelled` as for `failed`, and reading that mark produced a confident diagnosis that blamed a new test and nearly had a correct fixture rewritten; the job had run **zero steps**, which is a thing no test can cause. Classify before rerunning — a step that failed, a job cancelled with steps, a job cancelled with none, and an error at `Set up job` before checkout are four different findings — and rerun at most once without a new classification. Poll no faster than once a minute: a twenty-second loop earned an HTTP 403 secondary rate limit that made a scheduled rerun *silently not fire*, which is the worst shape a failure can take, since no answer was read as a good one. After any `gh` call that does not return success, re-read the run's state before believing anything about it.
* Keep design-project commits and skill-repository commits separate. Do not modify the skill repository during an ordinary commission unless reusable learning or a confirmed defect justifies it.
* Run all relevant formatting, lint, type, unit, integration, replay, packaging, and link checks. Independently review consequential skill changes.
* A green suite establishes what the code does and nothing about why a comment says it does it. Open every citation you write — a section number, a function name, a quoted sentence, a measured figure — against its source before shipping it. Unchecked justifications are this repository's most common defect: a convention cited from a sibling that had only its harmless half, a function name that did not exist, a section number naming a different section, a quotation the document does not contain, and a figure the citing file's own fixture does not produce.
* Prove a protection by mutating it, never by watching it pass. A check that cannot fail reads exactly like one that holds: a sweep can assert every rule while nothing runs them, a constant asserted against itself cannot notice it shrinking, a golden can pin a library's tessellation instead of the rule it names, and a fixture whose two states are identical distinguishes neither. Where the defect is a missing argument or an unmade call, only a test that observes the call can see it — endpoint tests, source greps and result comparisons all pass.
* Finish only when project artifacts and learning records are saved, current evidence is reported honestly, and remaining user action is limited to genuine decisions or physical testing.
